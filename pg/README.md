# pg/ — Postgres-схема (SaaS Этап 0, Шаг 1)

Боевой салон **не трогается**. Это заготовка новой базы для мультитенантности.

## Файлы
- **`generate.py`** — генератор: берёт реальную боевую схему SQLite и собирает
  из неё Postgres-схему (типы через sqlglot, + `tenant_id`, + пер-тенантные
  уникальности, + RLS). Источник: `/tmp/prod_schema.sql` (дамп `sqlite_master`
  с сервера, только структура — данные клиентов не выгружались).
- **`01_schema_postgres.sql`** — СГЕНЕРИРОВАННЫЙ результат. Руками не править —
  менять `generate.py` и пересобирать.

## Пересобрать
```bash
# 1) снять свежую структуру с сервера (только метаданные):
ssh ... 'cd ~/barbershop-bot && venv/bin/python -c "import sqlite3;
  [print(f\"-- [table] {n}\n{s};\n\") for t,n,s in
   sqlite3.connect(\"barbershop.db\").execute(
   \"SELECT type,name,sql FROM sqlite_master WHERE sql IS NOT NULL\")]"' > /tmp/prod_schema.sql
# 2) сгенерировать + проверить:
python3 generate.py
```

## Что заложено (главные решения)
- `INTEGER → BIGINT` (telegram/record id бывают > 2.1 млрд).
- `AUTOINCREMENT → GENERATED BY DEFAULT AS IDENTITY` — «BY DEFAULT», чтобы при
  миграции вставлять СВОИ id и сохранить связи (FK).
- `tenant_id` в каждой таблице (+ FK на `tenants`).
- 🔴 **Пер-тенантная уникальность**: `clients.telegram_chat_id`,
  `admins.telegram_user_id`, `masters_telegram.*`, коды, `settings.key` —
  стали `UNIQUE(tenant_id, ...)` / составным PK. Один человек может быть
  клиентом нескольких салонов.
- **RLS** на каждой таблице: приложение делает `SET app.tenant_id='<id>'`, и
  Postgres физически не отдаёт чужие строки — страховка от утечки ПД.

## Статус
Схема проверена ПАРСЕРОМ Postgres (sqlglot), все 33 `CREATE TABLE` и 54 индекса
валидны. На ЖИВОМ Postgres ещё не исполнялась — это следующий шаг (локальная
репетиция миграции ИЛИ прогон на Yandex Managed PostgreSQL).
